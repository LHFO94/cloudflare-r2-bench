# R2 load-test harness

Drives sustained, high-rate `GetObject` traffic at Cloudflare R2 from load
generators running outside Cloudflare, and reports latency and throughput from
the client's point of view.

The design target is **80,000 requests/second** of plain S3 GETs against 25 R2
buckets, generated by 8 GCE VMs, but nothing about the stack is pinned to those
numbers or to that cloud account. `terraform apply` in a fresh project with a
fresh `deployment_id` gives you an isolated copy.

---

## How it works

```
  Operator ──▶ Worker control plane ──▶ D1 (jobs, agents, metrics)
                      ▲    │
             poll for │    │ assignment: slot, RPS share, start/stop instants
             work,    │    ▼
             push     └── GCE load agents (Go) ──▶ R2 S3 API
             metrics
```

**Control plane** — a Cloudflare Worker. It holds the job definition, hands out
one slot per agent, records the metrics agents push, and serves the operator UI.
It never reaches out to an agent, which is what lets the load generators live
anywhere with outbound HTTPS.

**Agents** — a Go binary on GCE VMs. Each polls for work, is told its own share
of the aggregate RPS and a shared wall-clock start instant, warms its connection
pool, then drives an open-loop, rate-paced GET workload and reports every 10
seconds.

**Storage** — N R2 buckets seeded with a fixed keyspace of small objects, in a
location colocated with the load generators.

### Design notes

*Agents pull, they are not pushed.* The control plane has no inbound path to a
VM. Adding capacity means booting more VMs; they find the job themselves.

*Open-loop pacing.* A token bucket issues requests at the target rate regardless
of whether earlier ones have returned. Closed-loop pacing (fire the next request
when the previous completes) silently reduces offered load exactly when the
system under test slows down, which is when you most want the load held steady.

*Percentiles are computed on the agent.* Each agent keeps a local log-linear
histogram and reports p50/p95/p99 per interval. Averaging per-agent means in the
database would hide the tail this test exists to measure.

*Synchronised start.* Every agent on a job receives the same `startAtEpochMs`
and holds until it. Otherwise the fleet ramps in stages over a poll interval and
the aggregate never cleanly reaches the target.

*One job at a time.* Agents poll for "the" open job; a second concurrent job
would steal their slots. The control plane rejects the second start.

*HTTP/1.1, not h2.* GCP caps a single TCP flow at about 3 Gbps and HTTP/2 would
multiplex the whole agent onto a handful of connections. The agent explicitly
disables h2 and runs a large connection pool.

*Direct external IPs, not Cloud NAT.* A shared NAT gateway would exhaust port
allocations and become the bottleneck long before R2 did.

*Reconciliation by cron, not by a job-carrying message.* A minutely sweep closes
expired jobs and fails agents that stopped reporting. A missed tick resolves on
the next minute; a lost queue message would hang a job forever.

## Prerequisites

- Terraform >= 1.6, Go >= 1.25, Node >= 20, `gcloud`
- A Cloudflare account with R2 enabled
- A GCP project with enough vCPU and in-use external IP quota in the target
  region (8 x `n2-standard-8` needs 64 vCPU and 8 IPs)

## One-time setup

### 1. Cloudflare API token

Needs **Account / Workers Scripts / Edit**, **Account / D1 / Edit** and
**Account / Workers R2 Storage / Edit**.

```bash
export CLOUDFLARE_API_TOKEN='...'
```

Used by both Terraform and wrangler. Never put it in a tfvars file.

### 2. R2 S3 credentials

Create an R2 API token under R2 > Manage API tokens. **Scope it to the
`r2bench-*` buckets, not the whole account.**

That scoping is the actual security control here, so it is worth doing properly.
The credential reaches the VMs through **instance metadata**, which means it is:

- readable by anyone with `compute.instances.get` on the project — on
  `globalse-198312` that is the `se@`, `cse@`, `im@` and `sirtsquad@` groups
- recorded in `terraform.tfstate`, which has no remote backend configured
- written to `/etc/r2agent/agent.env` on each VM at mode 0600

Secret Manager would avoid all three, but granting a VM read access needs
`roles/secretmanager.admin`, which on this project is held only by
`sxpadmin@cloudflare.com`. Metadata is what the available permissions allow. A
bucket-scoped token makes the worst case "someone deletes disposable benchmark
fixtures" rather than "someone deletes production objects".

Pass them as environment variables, never in a tfvars file:

```bash
export TF_VAR_r2_access_key_id='...'
export TF_VAR_r2_secret_access_key='...'
```

Rotate the token after a run.

#### Chicken and egg: create the buckets first

R2's token UI can only scope to buckets that already exist, so the buckets have
to be created before the token. Apply the R2 module on its own, then come back:

```bash
cd terraform/envs/smoke
terraform init

# Placeholders: the R2 module does not use them, but Terraform requires a value.
export TF_VAR_r2_access_key_id='pending' TF_VAR_r2_secret_access_key='pending'
terraform apply -target=module.stack.module.r2
```

Now the `r2bench-<deployment_id>-NN` buckets exist. Create the scoped token
against them, re-export the real values, and continue with the full apply.

### 3. Enable GCP APIs

```bash
gcloud config set account luuk@cloudflare.com   # not the personal account

gcloud services enable compute.googleapis.com storage.googleapis.com \
  --project=globalse-198312
```

If you lack `serviceusage.services.enable`, ask a project owner; this is the one
step Terraform cannot do for you.

### Permissions this stack assumes

Terraform needs `compute.admin`, `storage.admin` and `iam.serviceAccountAdmin`,
all of which the SE groups hold on `globalse-198312`. It deliberately creates
**no project-level IAM bindings**, because `resourcemanager.projectIamAdmin` is
not available — see [Watching a run](#watching-a-run) for what that costs.

## Running a benchmark

### Step 1 — smoke test first

The smoke environment is one VM, three buckets and a 2,000-key keyspace. It
exercises every failure mode the standard run has — Worker deploy, D1
migrations, agent boot, secret fetch, SigV4 signing, metrics reporting — for a
few cents. The standard run costs roughly $31 for 15 minutes, dominated by R2
Class B operations at about $104/hour, so do not discover a signing bug there.

```bash
make build-agent

cd terraform/envs/smoke
cp terraform.tfvars.example terraform.tfvars   # then edit
terraform init
terraform apply
```

### Step 2 — seed the buckets

Buckets come up empty. Seed them once per deployment:

```bash
eval "$(terraform output -raw seed_env)"
export R2_ACCESS_KEY_ID='...' R2_SECRET_ACCESS_KEY='...'

cd ../../..
go run ./cmd/seeder -dry-run   # prints object count and estimated Class A cost
go run ./cmd/seeder
```

Re-running is safe. The seeder writes a sentinel object per bucket and skips any
bucket already holding the expected shape, because every PUT is billable.

### Step 3 — run it

```bash
cd terraform/envs/smoke
terraform output -raw dashboard_url    # open this
```

The URL carries the admin token. It is captured into `sessionStorage` and
stripped from the address bar on load, so it does not end up in your history or
in a screenshot.

Set **Agents** to the value of `terraform output agent_count` — the control
plane divides the aggregate target across exactly that many slots and will not
admit more.

### Step 4 — the standard run

Same sequence in `terraform/envs/standard`. Use a **different `deployment_id`**;
the two stacks are fully independent.

### Step 5 — tear down

```bash
terraform destroy
```

The GCE fleet is the recurring cost and it stops the moment the MIG is deleted.
Buckets and their seeded objects survive a `destroy` only if you delete the
stack selectively; a full destroy removes them, and reseeding is another Class A
bill. If you plan a follow-up run within a few days, destroy only the
load-generator module:

```bash
terraform destroy -target=module.stack.module.loadgen
```

## Operating notes

### Sizing

Each VM is capped by GCP at **1.8 Mpps or 30 Gbps of internet ingress**, flat,
regardless of machine size. At a 1500-byte MTU that is roughly 21.6 Gbps of
usable ingress per VM. With ~1.5 KB objects at 10,000 RPS per VM the standard
run uses about 1.2 Gbps in aggregate, so the fleet is sized for CPU headroom on
TLS and syscalls, not for bandwidth.

`network_performance_config` / Tier_1 is deliberately not set: it raises
*egress* only, and this workload's egress is a trickle of GET headers.

Spot VMs are not used. `PREEMPTIBLE_CPUS` quota is zero in the target project,
and a preemption mid-run would invalidate the measurement anyway.

### Watching a run

The watch page is the primary view. For the VMs themselves:

```bash
terraform output -raw list_instances_command   # instance names
terraform output -raw logs_command             # serial console for one VM
terraform output -raw ssh_command              # IAP tunnel into one VM
```

Then substitute a real instance name for `<suffix>`.

**There is no fleet-wide log view.** Shipping to Cloud Logging needs
`roles/logging.logWriter` on the agent service account, and granting any
project-level role needs `resourcemanager.projectIamAdmin`, which on
`globalse-198312` belongs to `jeffh@cloudflare.com` alone. So the agents are
granted nothing at project level and their output stays local: serial console,
or `journalctl -u r2agent -f` over SSH.

In practice this matters less than it sounds. The metrics you actually care
about are pushed to D1 and rendered on the watch page; the logs are only for
diagnosing a VM that failed to boot, and the serial console is better for that
anyway because it captures failures from before SSH is up.

Port 22 is reachable only from Google's IAP range, even though the VMs carry
external IPs.

### Pulling raw results

The UI aggregates per minute. For per-agent, per-interval samples:

```bash
npx wrangler d1 execute DB --remote --config wrangler.generated.jsonc \
  --command "SELECT SPAWN_ID, TICK_NUMBER, RPS, LATENCY, P95, P99, STATUS_5XX
             FROM JOB_SPAWN_METRICS WHERE JOB_ID = '<job-id>' ORDER BY CREATED_AT"
```

### Reading the numbers

`STATUS_4XX` climbing means a seeding or signing problem on our side — most
often a keyspace mismatch between the seeder and the agents. `STATUS_5XX` means
R2 shed the request. They are counted separately because conflating them wastes
a run.

If achieved RPS sits below target while latency stays flat, the agents are
CPU-bound, not R2. Check `Reporting agents` on the watch page first: a VM that
died mid-run is marked `FAILED` after 90 seconds without a report, and its share
of the target simply goes unserved.

## Local development

```bash
cp .dev.vars.example .dev.vars
npm install
npx wrangler dev          # ADMIN_TOKEN empty disables the operator auth check
make test                 # Go + Worker suites
make check                # adds Terraform fmt and validate
```

The checked-in `wrangler.jsonc` is the local-dev config. Deployed environments
use `wrangler.generated.jsonc`, rendered by Terraform so the Worker name, D1 id
and account id match the environment being provisioned. Do not edit the
generated file.

## Relationship to upstream

Forked from [`Dabz/cloudflare-r2-bench`](https://github.com/Dabz/cloudflare-r2-bench).
The Worker control plane, D1 schema and UI are evolved from it. The Java
container-based load generator was removed and replaced with the Go agent and
Terraform-managed VMs:

- the original read response bodies one byte at a time, which measured the
  client's read loop rather than R2;
- it fetched a single fixed key, so results reflected caching;
- it paced closed-loop, so offered load fell whenever R2 slowed;
- it ran on Cloudflare Containers, which places the load generator inside the
  network being measured.
